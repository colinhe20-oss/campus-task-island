## R1 已退役 提前取消的志愿活动造成永久注销拦截

**原版本位置（对应逻辑已移除）：** `campus/accounts.py:60-68`；对照 `campus/volunteers.py` 的 `_qualified()`、`cancel_activity()`、`update_record()`。

复现步骤：

1. 负责人创建尚未开始的志愿活动，参与者获得一个岗位名额。
2. 负责人在岗位开始前取消整场活动，报名状态变为 activity_cancelled。
3. 等原岗位开始时间过去，再尝试注销负责人账号。

实际：注销检查把该报名当作待登记或待核验记录，注销返回409。尝试登记“未参与、0分钟”也被志愿服务拒绝，因为活动在开始前已经取消，不具备参与核验资格。等待到活动结束仍不会消除这一拦截。

原因：注销 SQL 只要求报名为 registered/activity_cancelled 且原岗位已开始，没有复用志愿核验资格规则，遗漏取消时刻与岗位开始时刻的关系，及开始前是否实际获位。原本 pending/waitlisted 后被提前取消的报名也可能落入同类错误条件。

影响：负责人没有可通过正常业务操作消除的注销拦截项。

建议：将“该报名是否产生待核验义务”的判断收敛到共享规则。只有确实具备 `_qualified()` 等价资格且缺少应有记录时才拦截；分别覆盖提前取消、开始后取消、候补未转正和已确认小时。

探针：`test_cancelled_unstarted_volunteer_does_not_permanently_block_owner`。使用可控时钟，注销请求实测409；志愿登记同时被拒绝。

## R2 已退役 未完成结算确认仍可注销

**原版本位置（对应逻辑已移除）：** `campus/accounts.py:35-39`；对照 `campus/todos.py:47-67` 和 `campus/terms.py` 的结算确认。

复现步骤：有偿任务正常申请、接取、提交和验收，任务进入completed；付款方和收款方都没有进行结算确认；发布者提交本人注销请求。

实际：账号页返回can_close=true、blockers=[]，注销返回200，并使账号无法再登录。此时结算记录仍未完成双方确认，另一方不能代替已注销用户确认。

原因：注销检查只覆盖published/in_progress/pending_review/paused等任务状态，没有检查终态任务仍存在的结算事项。首页与个人待办则明确将这种结算保留为待办或等待事项。正金额的取消结算存在同类遗漏，需要修复时一并覆盖。

影响：账号永久注销后，结算确认流程可能无法完成。保留业务历史不会恢复已注销账号的操作能力。

建议：明确结算完成前的注销规则，并使注销、待办和结算使用同一判断。按当前“处理完未完成事项后注销”的规则，双方尚未确认的正金额结算应阻止注销；若产品希望允许退出，应先设计替代的终结方式及界面说明。

探针：`test_unsettled_completed_task_blocks_account_closure`，预期409，实际200。未将其描述为真实支付发生或丢失；本项目仅记录双方声明。

## R4 已修复 引航员岗位搜索分页漏项与总数错误

**位置：** `campus/volunteers.py` 的 `search_jobs()`；`tools/campus.py` 的 `volunteer_search()`。

复现：创建一个包含6个岗位的志愿活动，调用search_volunteer_jobs(limit=5,offset=0)，再调用offset=5。

实际：首批5项，total=5；第二批0项，第6个岗位被跳过。

原因：底层volunteers.search的limit/offset针对活动，工具返回的items却是岗位。代码先按活动分页，再展开并截取岗位，两个分页单位不同；total又被设成本批len(items)。

影响：模型不能按分页遍历匹配岗位，也可能误以为只有5个结果。用户不必构造大量数据，一场6岗位活动即可触发；直接调用志愿活动HTTP列表不受这一工具分页错误影响。

修复：新增岗位级`search_jobs()`，在同一个只读事务、同一个服务端时钟下轻量检索候选岗位，用Python casefold保持Unicode大小写不敏感匹配；按活动开始时间、活动ID、岗位顺序、岗位ID排序，匹配后计数，再按岗位分页。仅补充当前页涉及活动的详细状态，并为同一活动复用一次读取。工具保留原字段、链接、名额与本人报名信息，total改为全部匹配岗位数。网页原有活动级search不变；不额外隐藏满额、报名截止或尚未开放的活动，也不改动数据库结构与历史数据。

验证：`tests/test_volunteer_job_search.py`共12项通过，包含原总数和第二页探针，以及跨活动稳定分页、关键词匹配与Unicode大小写、空结果和越界、活动可见性、实时名额及本人隐私、单次时钟与按活动复用、只读无副作用、查询期间发生报名时的快照一致性、原活动分页和工具参数校验。原两项探针已从audit迁入该正式回归文件，由现有CI的unittest discover自动执行。完整后端回归312项通过（252.340秒）；未改写正式数据库或创建Git提交。

## R6 已修复 同步模型接口把截断输出当作成功

**位置：** `backend/client.py` 的 `chat()`、`chat_stream()` 和 `_check_finish_reason()`，同步调用入口为POST /api/guide/chat。

复现：MockTransport返回一个协议响应，finish_reason="length"，message.content="TRUNCATED_ANSWER"。不访问真实模型。

实际：同步引航员接口返回200，答复为TRUNCATED_ANSWER，并走正常历史提交和成功记录路径。

原因：非流式chat()直接归一化message，忽略choices[0].finish_reason；同文件的流式实现已拒绝length等不完整终止。同步兼容接口与通用CLI使用非流式路径。当前网页的常规异步运行使用流式路径，不能据此声称网页流式防护失效。

修复：真实HTTP适配层在归一化消息、交给Agent执行工具之前检查终止原因，同步与流式共用stop/tool_calls白名单；截断、过滤、未知或缺失的最终终止原因抛出受控ValueError。同步响应额外检查候选列表与消息结构，避免空候选等情况抛出未处理的IndexError。流式中间片段允许null，保留整条流必须完整结束的规则。复用现有引航员502、失败运行记录及暂存提交机制，不改变FakeBackend内部协议；原HTTP模拟测试补齐合法的finish_reason。

验证：`tests/test_completion_status.py`共12项通过，覆盖正常回答与usage、正常工具调用、异常/缺失终止原因、异常响应结构、截断响应的合法工具参数不执行、同步接口502与失败记录、失败后重试、新旧会话中暂存草稿和阶段建议不落库、原有历史版本保留，以及流式协议与异步运行截断回归。完整后端回归332项通过（306.198秒），原audit兼容入口12项通过。均使用MockTransport和临时数据库，不调用真实模型；未改写正式数据或创建Git提交。

原探针`test_nonstream_truncation_is_not_persisted_as_success`已迁入正式回归；`audit/review_20261016.py`保留为这组测试的兼容入口，现应成功退出。已有草稿、业务与对话记录不因失败改写，失败运行记录正常保留。
