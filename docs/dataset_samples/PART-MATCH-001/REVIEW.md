# PART-MATCH-001：参与者偏好、机会推荐与提醒

版本：1.0.0-candidate。状态：用户已审核接受；数值总分未指定。运行结果独立保存，不把规格完成、系统通过和用户接受混为一谈。

## 1. 场景与输入

本组连接已审核的书信志愿和小满游园样本，包含12名合成参与者、2场活动、24个人物—机会判断、3条自然语言偏好与推荐解释对话、12项业务生命周期检查。

两个活动由原样本金标准通过真实业务服务创建在独立实验库中。不用模型曾漏字段的实际草稿作为世界真值，避免组织者生成错误污染推荐评测；原对话中的错误继续保留。

| 机会 | 模拟安排 | 参与时间口径 |
|---|---|---|
| V：集中读信与回信 | 2027-05-23 14:00—16:00，8名审核岗位 | 必须全程参加 |
| A：小满墨艺手作游园 | 2027-05-23 12:00—17:00开放，60名直接报名 | 可在开放时段内到场，无须全程 |

书信样本从原2026-10-18基准整体平移到2027-05-16，所有活动、岗位、报名时间一致平移；游园保持原模拟时间。观察时点为2027-05-16 13:00，北京时间，已过12:00报名开放。原两条冻结规格保持不变，转换后业务输入另存。

人物为模拟浙大学生，自述不等于学校认证。兴趣不等于具备技能，推荐不等于报名、获得名额或取得认定。兴趣与时间偏好都只用于模拟，不是真实学生资料。

## 2. 人物与独立判断依据

R＝应推荐候选；C＝可推荐但须明确核对未知条件；X＝不应对该用户推荐。标准答案根据活动规则与人物条件预先人工编写，不调用当前匹配代码反推。

| 人物 | 主要条件 | V | A |
|---|---|:---:|:---:|
| P01 | 书信、公益；会回信；14—16点；仅志愿 | R | X |
| P02 | 手作、传统文化；12—17点；仅综素 | X | R |
| P03 | 书信、公益；15—17点；仅志愿 | X | X |
| P04 | 手作、传统文化；仅14—15点；仅综素 | X | C |
| P05 | 书信、公益；未登记空闲；仅志愿 | C | X |
| P06 | 只对篮球感兴趣，与活动地点相同 | X | X |
| P07 | 同P01，但已有志愿活动待审核申请 | X | X |
| P08 | 同P02，关闭站内机会提醒 | X | R |
| P09 | 两类兴趣均有，12—17点空闲，两类均关注 | R | R |
| P10 | 两类均相关，但偏好已在观察时点前过期 | X | X |
| P11 | 两类均相关，12—17点空闲但14—16点不可参加 | X | C |
| P12 | 兴趣仅说“传统文化”，12—17点空闲；仅综素 | X | R |

除P08外，人物已授权后均开启提醒。P07的待审核记录由业务服务真实创建，不手写报名状态。

关键对照：P03不能完整参加固定志愿岗位，应该排除；P04和P11仍可错时游园，但需核对体验耗时及集章条件，不能承诺拿到0.15或0.5分。P05不应被假定有空，推荐解释须指出时间未核实。P08只关闭消息，不关闭推荐列表。P12检验语义相关性，允许当前关键词算法漏掉它，但不能因此改成X。

不规定两个机会的唯一排序，不人为填“匹配成功概率”。平台排序分只作排序数据；在这么小的候选集中不计算NDCG或宣称大规模推荐效果。

## 3. 三条实际对话

P01、P02、P04各有一条冻结的自然语言偏好首句，见`gold.json.natural_messages`，例如：

> 我会回信，兴趣是书信、公益，优先紫金港。只关注志愿服务。我在2027年5月23日14:00到16:00有空，按北京时间，只是这一次，不是每周。请帮我登记成待核对偏好，我希望确认保存后通过站内消息提醒新机会。

流程：

1. 为实际对话创建全新参与者账号，正式偏好版本为0；只发自然语言，不把期望JSON或答案放进模型上下文。
2. 保存真实回复、工具轨迹与偏好提议，核对一次性时段、兴趣、技能、地点、类型和提醒意愿。
3. 提议须在用户确认前保持未授权，不得产生该用户机会提醒。仅在忠实性核对通过后，执行者模拟用户独立确认；不替模型修复字段。
4. 确认后使用实际语义解析和匹配服务生成机会；解析未就绪时明确记录关键词回退，不伪装成语义结果。
5. 让Agent查询本人已保存偏好与当前推荐，解释依据和待核对条件。报名仍由用户决定，本条模型对话不代报名。

原话有兴趣却没说技能时，不得加“会书法”“擅长手工”。一次性空闲不得变成每周重复。不能把站内提醒授权扩大到邮件、短信或向其他人发消息。

自动忠实性检查是保守门槛；即使语义上合理的措辞因检查未通过，也保留实际提议并提交人工审核，不自动计为模型失败或强行确认。

## 4. 推荐与业务验证

先在同一人物与活动快照运行真实关键词回退，再运行真实LLM语义解析后的推荐。保存每项实际`matching_method`、证据、理由、核对项及解析状态；语义失败时保留真实回退，不填造标签。

匹配服务扫描读取数据库，不在扫描中调用模型。语义解析是独立任务；采用现有缓存和重试规则，两个工作线程处理真实解析任务，读取和业务时间固定。轮询、重启、偏好确认等产生的站内机会提醒以实际通知表为准。

另用独立生命周期库执行12项检查：

| 编号 | 情境与预期 |
|---|---|
| L01 | 偏好保存但活动未发布时无机会 |
| L02 | 发布后无聊天也能由后台扫描触达，不推荐本人发布的活动 |
| L03 | 重复扫描不重复提醒 |
| L04 | 重启后保留推荐且不重复提醒 |
| L05 | 用户忽略后不重新出现 |
| L06 | 关闭提醒后，新机会仍显示但不产生机会消息 |
| L07 | 本人已有待审核报名时，原招募推荐失效 |
| L08 | 退出报名可恢复推荐，但不重复发旧机会提醒 |
| L09 | 岗位满额后推荐失效 |
| L10 | 释放名额后恢复推荐且提醒去重 |
| L11 | 活动取消后对应推荐失效 |
| L12 | 到报名截止瞬间不再推荐 |

生命周期库为L06增加一场明确标注的游园衍生活动，并为满额测试创建模拟填位账号。这些不是主世界新增的独立活动样本，不混进24对评测。

## 5. 判定、交付与审核

对24对分别比较是否展示候选。R和C合为应展示，计算precision与recall，并单独审核C的解释条件。硬排除对象被推荐、遗漏可参与对象、只靠地点命中、将未知时间或资格说成满足，分别记录。零分母记null，不伪造0或100%。

偏好提取、用户确认、推荐召回、解释忠实、提醒去重分别评价，不把单一端到端结果归因给所有模块。实际前置条件失败的后续步骤记未执行，不自动判错。系统当前不支持自由到场的时间模型时，保留P04/P11的独立标准答案和漏推荐，不改活动设定或人物时间迎合实现。

结构化底稿与24项判断在`gold.json`；静态检查在`validation.json`；核心文件摘要在`manifest.json`。运行写入独立新目录，保留world.sqlite3、来源快照、时间转换、真实ID映射、关键词结果、语义结果、通知和生命周期记录、3条真实对话。无真实密码、密钥或个人资料导出。

12个人物共享两个活动原型，本组属于公开开发与演示集。24对不是24个独立活动，也不能据此推断总体用户提升比例或统计显著性。后续扩展需增加活动种类、更多候选与独立用户审核。

审核记录：用户已接受本样本组。该接受表示场景与规格可用，不等于数值评分满分或系统评测通过。24对推荐、12项生命周期、3条真实对话的结果仍按各自记录保留。
