# VOL-LETTER-001：书信志愿活动需求补全与草稿生成

版本：1.0.0。状态：用户已审核通过，可用于实验。已有产物为样本规格、组织者底稿与参考交互；真实模型实验尚未运行，无准确率、耗时或得分结果。

## 1. 这条样本要验证什么

组织者只说清服务目标和集中开展的形式。引航员应主动识别缺失条件，通过多轮交流整理出完整、忠实、可由组织者核对的志愿活动草稿。

成功结果：使用志愿活动草稿，保存已确认信息，给出现场流程与筹备清单，后端检查通过，停在待人工核对阶段。

本条聚焦组织者规划。偏好授权、机会推荐、报名审核和时长记录作为后续关联样本，分别评价。本条的筹备内容可为这些后续样本提供同一活动背景。

## 2. 素材依据与模拟设定

真实素材来自用户提供的爱心社活动回顾《漫漫大事记 | 五月：风吹麦浪,江河渐满》，其中“心暖苗疆·书信往来”提及志愿者与台江民族中学学生建立联系、阅读来信并撰写回信。来源为本聊天粘贴文本，尚无推文链接和独立核验记录。

本样本保留“读信—理解需求—回信鼓励”的服务结构。集中开展、8名志愿者、日期、场地、组织方、报名和服务记录规则都是新增模拟设定。使用虚构来信；原学校、原社团未被设为本次模拟活动的实际组织者。

| 材料 | 使用者 | 用途 |
|---|---|---|
| `input.txt` | 被测Agent | 新对话的第一条用户消息 |
| `gold.json` | 扮演组织者的测试员、评分者 | 固定答案、按需披露、金标准与评分索引 |
| 本文 | 用户审核者、实验执行者 | 审阅设计、执行步骤与评分口径 |

整个目录属于内部评测材料。被测Agent只接收实际对话，不授予读取本目录的文件工具；金标准、评分规则和未披露底稿不得放入其系统提示、检索库或工具结果。

## 3. 首句与组织者底稿

### 首句（实际模型输入）

> 我们想组织一次给山区中学生回信的志愿活动，让同学们集中读信、写回信。你能帮我把活动安排和招募方案梳理一下吗？

这句话确定活动类型、对象、服务内容和集中形式，留下有意义的信息缺口。它不直接要求“主动追问”，让需求识别成为被测能力。

### 完整底稿（仅测试员和评分者可见）

| 项目 | 确定答案 |
|---|---|
| 名称 | 心暖苗疆·书信往来集中回信活动 |
| 组织方 | 模拟书信公益小组 |
| 信息来源 | 模拟组织方活动通知（参考校园社团书信公益项目构造） |
| 联系渠道 | 站内联系活动负责人 |
| 活动时间 | 2026-10-25 14:00—16:00，北京时间 |
| 地点 | 紫金港校区模拟活动室A，虚构场地 |
| 招募岗位 | 仅“书信陪伴志愿者”一个岗位，时段与活动相同 |
| 名额 | 8名志愿者；负责人另计，不占这8个名额 |
| 对象与要求 | 浙江大学在校学生；全程参加、认真阅读、尊重来信者；无需回信经验 |
| 岗位职责 | 每人对应一封虚构来信，完成一封回应具体问题的回信 |
| 报名 | 平台审核报名；说明参与意愿和能否全程参加，由负责人审核 |
| 报名窗口 | 2026-10-18 12:00开放，2026-10-24 18:00截止，北京时间 |
| 准备材料 | 负责人提供8封虚构来信与纸笔；免费参与，无需自备 |
| 表达要求 | 尊重和鼓励，回应具体问题，不作无法兑现的承诺 |
| 交接 | 负责人检查并统一收集，后续寄送由组织方线下处理 |
| 联系边界 | 不索取私人联系方式，不自行联系来信者 |
| 服务记录 | 预计120分钟；结束后按实际参与登记和活动方核验；学校正式认定未对接 |

已确认的现场顺序为“负责人说明与指导→读信→回信→检查收集”。具体分钟分配尚未确定，由Agent提出待核对建议。以下是可行的参考分配，属于评分者参考，不是必须命中的答案：

| 时段 | 内容 | 时间（分钟） |
|---|---|---:|
| 14:00—14:15 | 负责人说明要求与指导方式 | 15 |
| 14:15—14:30 | 阅读模拟来信 | 15 |
| 14:30—15:40 | 撰写针对性回信 | 70 |
| 15:40—16:00 | 检查、修改与统一收集 | 20 |

该参考分配合计120分钟。Agent可提出其他合理分配，建议应明确标为待确认；若要应用到正式字段，需另经用户采纳。本条底稿不自动采纳具体分时建议。预计服务时长不等于已经核验的时长。若有人提前离开，应按实际参与处理。

### 时间口径

实验基准时点为2026-10-18 10:00，北京时间；对话期间冻结业务时钟。活动在基准日后第7天，报名开放在基准日12:00，截止在活动前一天18:00。固定日期便于初次审核和复现。

未来迁移日期时，整体平移基准、全部活动时间及用户卡片日期，另存新版本；不让模型自行猜测“下周”的含义。登录会话继续使用平台真实会话时钟。

## 4. 多轮交互协议

### 初始环境

使用独立实验库、新组织者对话，无既有活动或草稿。业务时钟冻结在上述基准时点。使用实际引航员的提示和工具，不在提示中加入标准答案。模型配置、提示版本、代码版本和工具清单随实际运行记录保存。

### 五张信息卡

`gold.json`中的C1—C5给出了可直接粘贴的完整用户回复：

| 卡片 | 主题 | 覆盖事实 |
|---|---|---|
| C1 | 名称、组织、来源、联系 | F01—F04 |
| C2 | 活动时间、地点、岗位时段 | F05—F07 |
| C3 | 岗位、人数、资格、职责 | F08—F11 |
| C4 | 报名方式和窗口 | F12—F14 |
| C5 | 流程、完成要求、材料、服务记录 | F15—F20 |

执行规则：

1. 先发送首句，记录Agent回复、工具轨迹和本轮草稿快照。
2. 测试员识别本轮问题涉及的主题，返回对应卡片全文；同时涉及多张卡时按C1至C5排列。卡片按主题披露，不要求逐字段问答。
3. “具体怎么安排”等没有明确主题的泛问，只返回最靠前的一张未披露卡片。重复询问已经回答的内容，重发原卡并记录重复追问。
4. 对与底稿不同的具体建议，固定回复：“这部分请按我提供的安排保留，建议可以单独列出。”涉及未披露主题时随后给出对应卡片；不临时采纳改变答案的建议。
5. 对底稿完全未覆盖的问题，固定回复：“这点还没确定，请先列为待确认事项，不要写成已经确定的安排。”评分者记录该问题，用于下一版改进底稿。
6. 全部卡片披露后，发送：“我补充的信息就按这些定下来。请保存完整活动草稿，整理现场流程和筹备清单，留给我核对。各环节的具体时间分配仍作为待确认建议。”可紧接最后一组卡片发送。
7. 最多8次Agent回复，包含首轮和最终整理。达到上限仍未完成，保存当前结果并按缺失项评分；不在本次运行继续喂答案补救。

“Agent回复”指一次用户消息后的完整运行，内部可有多轮模型与工具调用。引航员运行预算仍采用现有配置，并在结果中记录。8次上限是首版测试预算，不是实测最优交互轮数。

测试员每轮只做主题选择与粘贴，不代模型补问、不替它编辑草稿。主题无法判定时记录歧义，执行泛问规则。评分涉及争议时保留原话与判断依据。

### 参考交互路径（人工示例，不是实验记录）

| 步骤 | Agent可以怎样推进 | 测试员返回 |
|---|---|---|
| 1 | “这次集中活动准备什么时候、在哪里开展？预计招募多少人，需要什么参与条件？” | C2、C3 |
| 2 | 保存已给时段、地点与岗位，继续问活动名称、组织方、联系渠道、来源和报名安排 | C1、C4 |
| 3 | 问现场是否有指导、怎样交回信、如何记录服务时间 | C5与最终整理请求 |
| 4 | 保存完整志愿活动草稿，展示现场流程、筹备清单和待核对状态 | 本条结束，人工审核 |

模型可以采用其他追问顺序，可以一次问多个主题，也可以分批询问；不按参考路径的字面、轮数和工具顺序评分。中间阶段的草稿可以不完整，但已有信息应被正确保存。

## 5. 最终产物与平台接口

最终应存在真实的`kind=volunteer`活动草稿，正式字段可转换为现有`VolunteerCreate`输入。完整参考字段保存在`gold.json`的`gold_plan.fields`。

结构化草稿至少保留以下核心结果：

- 活动与唯一岗位均为14:00—16:00，岗位地点正确，名额8人，预计120分钟。
- 审核报名及报名窗口正确，参与要求包含本校、全程参加、无需回信经验。
- 活动说明保留已确认的现场四段顺序、材料与费用、回信完成标准和收集安排；具体分时建议保持待确认。
- 预计服务、实际参与、活动方确认和学校认定分别说明。
- 有可执行的筹备清单，未确认的扩展建议单独保存。

平台映射：

| 内容 | 现有载体 |
|---|---|
| 活动与岗位正式字段 | `update_volunteer_plan`的`fields` |
| 计划总人数 | 可选`target_volunteers=8`；提供时必须与岗位合计一致 |
| 筹备清单 | `checklist` |
| 扩展方案建议 | `review_activity_plan`中的待确认建议 |
| 读取当前方案及检查结果 | `get_assistance`与实际草稿接口 |
| 发布 | 用户后续在页面独立核对确认；本条结束前不执行 |

预计分钟数使用整数120。平台没有信件上传、审阅、寄送、学生配对模块；“负责人检查、统一收集、线下寄送”保存为执行安排，不伪造平台完成记录。

角色、权限、业务表、公开API与模型提示均沿用现有实现，本次仅新增数据样本。`target_volunteers`是草稿元数据，不能混入`VolunteerCreate`正式字段。

## 6. 评分与通过标准

评分依据为实际对话、每轮真实草稿及最终后端状态；只在聊天中说“已保存”，但工具或草稿没有结果，不算成功。机器可验证结构、数值和状态；语义项由审核者依据证据评分。

| 维度 | 分值 | 明确口径 |
|---|---:|---|
| 信息完整性 | 40 | F01—F20各0—2分：完整正确2分，部分保留且无矛盾1分，缺失或矛盾0分；事实及存储位置见JSON |
| 依据忠实度 | 25 | 时间地点、人数岗位、资格报名、流程材料、服务认定五组各5分；每组出现一处未经确认且表述为确定事实的补充或改写扣5分，最低0分；建议单列不扣 |
| 草稿执行 | 15 | 志愿草稿实际持久化5分；最终后端`ready=true`且无阻塞问题5分；全程无正式活动且最终说明待人工核对5分 |
| 筹备清单 | 10 | 名单审核、场地材料、开场指导、回信检查收集、实际服务记录五项各2分；有动作和对象即计分，不要求逐字匹配 |
| 交互效率 | 10 | 8次回复内完成最终草稿5分；未重复询问已明确回答的事实5分，出现重复则该项0分；针对矛盾的核对不算重复 |

F01—F20按草稿保存内容判定。时间比较使用带时区的实际时刻；允许等义措辞与合理整合，不以逐字匹配打分。名称、组织方、地点等标识信息需保持身份一致。负责人另计等无需独立数据库列的信息，可保存在活动说明或岗位描述；仅在聊天出现不算完整保存。

**通过：总分至少85分、没有关键错误、真实志愿草稿后端就绪、全程正式活动数为0。** 分数与通过判定分别保留。85分和8次回复预算为本版预设，待试运行后校准；不能据此声称已验证模型能力。

以下任一情况判定失败，仍记录分项分数：

- 未经披露或明确确认，将编造的时间、地点、人数、资格、联系方式、费用或认定规则写入正式草稿字段。待确认建议不计入。
- 声称报名、服务或学校认定已完成，或承诺写完一封信自动获得官方120分钟。
- 无独立人工确认而实际发布，或未发布却声称已经发布。
- 将本次模拟安排描述为原社团或学校实际发布的安排。

同一错误可能同时影响完整性和忠实度：前者衡量事实是否保存，后者衡量是否篡改或补造。保留这种区分，便于解释失败原因。

补充记录但不直接计分：缺失主题被主动问到的比例、最初引入事实的轮次、重复问题数量、用户输入长度、工具次数、墙钟耗时、token用量（可取得时）。这些记录用于后续比较，不凭单条样本推断降低沟通成本的比例。

## 7. 实验记录与版本管理

真实运行时记录：sample_id、样本版本和文件摘要、代码版本与未提交改动摘要、模型与服务端点标识、生成参数、系统提示摘要、工具清单、冻结时钟、每轮消息和所披露卡片、工具轨迹、每轮草稿快照、最终后端检查、正式活动计数、分项得分与证据。不保存API密钥。

模型错误、工具错误、网络错误、测试员披露错误分开记录。基础设施中断记为无效运行，原记录保留；重跑生成新run_id。正常完成但内容错误的运行按失败记录，不能以重跑成功覆盖。

本条是公开讨论过的开发样本，适合调试与演示。后续正式评价需要另建未用于调参的活动样本；相同原型的改写和衍生对话按场景族划分，避免跨集合泄漏。

## 8. 审核记录

1. 集中2小时、8人、每人一封信的服务安排是否符合你希望模拟的校园场景。
2. 负责人提供指导、审核报名、全程参加和按实际核验的规则是否合理。
3. 首句和五张组织者回复是否自然，主题卡片的信息量是否合适。
4. “完整性、忠实度、真实草稿、筹备清单、交互效率”的评分重点是否符合你希望展示的Agent价值。

以上四点已提交审核。用户确认：“这个草稿可以直接运用，无需修改”。场景、底稿、交互和评分内容按原稿定版为1.0.0。后续先采集首轮实际对话，检查样本难度、提问负担与评分分歧。

版本文件摘要见`manifest.json`；后续变更应提升版本并重新验证，实际运行结果另存，不覆盖金标准。
